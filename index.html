§01

About

Engineer from Aveiro. Happiest where software meets hardware.

I studied computer engineering at the University of Aveiro: a BSc in Computer and Informatics Engineering, then an MSc in Computer and Telematics Engineering. The part I enjoyed most was always the same: the moment something leaves the simulator and meets the real world.

My MSc thesis was built around that moment. With support from Wavecom, I wrote a Lua service that runs on a production vehicle router and steers traffic between two 5G operators using radio metrics, RSRP and SINR, instead of only checking whether a link is up. Then I built the pipeline to measure it, put the router in a car and ran three road campaigns.

The result was not the one I expected. On the road, throughput could not be distinguished from the stock MWAN3 policy. Per-band calibrations showed why: signal quality alone ranks operators badly when they run very different channel bandwidths (10 vs 100 MHz). The thesis ends with a capacity model that takes bandwidth into account, and with a rule I now apply well beyond radio: measure the thing you actually care about.

I'm looking for a team where I can grow fast, in backend, networking or systems.

  1. MSc thesis · submitted Nov 2026

    Physical-layer metrics for cellular network selection in multi-WAN vehicle routers

    University of Aveiro · thesis supported by Wavecom S.A.

    Vehicle routers carry two cellular modems. The stock balancer (MWAN3) splits traffic by static weights and link liveness. Could radio metrics do better?

    • A Lua service on MWAN3 / OpenWrt (WaveOS 9), running on a production vehicle router, that adjusts multi-WAN weights from the RSRP and SINR of two 5G operators. No kernel changes.
    • Measured cost on the router: 0.5 ms of CPU per decision and 2.6 MB of memory.
    • Verified on the device how weights materialise: rules in the iptables mangle table and marks kept by conntrack.
    • End-to-end data pipeline: collection on the router (ubus/QMI, GPS, ICMP latency), writes over an HTTP API to InfluxDB, real-time Grafana dashboards in Docker.
    • Three road campaigns on the A1 (Aveiro–Mealhada, ~260 km) with more than 10 000 geo-referenced radio samples.
    • Throughput measured with iperf3 per policy, per operator and per 5G band (n28 / n78, SA / NSA).
    • Python analysis (NumPy, pandas, Matplotlib) with deterministic replay of recorded traces and block bootstrap.
    • In replay, time with traffic on the worse interface dropped from 34% to 27%.
    • On the road, throughput could not be distinguished from MWAN3.
    • Per-band calibrations showed that signal quality alone misranks operators with different channel bandwidths (10 vs 100 MHz).
    • Proposed a capacity model that includes bandwidth. Signal quality is not capacity.
    • Earlier phase: an OpenWrt router in GNS3 with links emulated by tc/netem, and a simulator with a real-time dashboard.

SignalFlow

Telemetry ingestion and query backend for fleets of cellular routers.

Problem

Hundreds of routers report radio and link metrics every few seconds. The backend has to accept bursts without dropping data, never store a sample twice, and answer "what did this device look like in the last hour" quickly.

How it works

  • Devices authenticate with hashed API keys and post batches; the API validates, rate-limits and answers 202 after appending to a Redis Stream.
  • A worker consumes the stream in batches, writes to PostgreSQL idempotently on (device, seq), and acknowledges only after commit.
  • Query API with cursor pagination and time-bucket aggregation in SQL (date_bin).
  • Overload answered with 503 and Retry-After (backpressure, load shedding), never 500. Benchmarked under open-loop load; the log records two bottlenecks found and fixed along the way.
  • Prometheus metrics, structured JSON logs, health and readiness checks. 60 tests against real PostgreSQL and Redis.

§05

How I work

Six rules, each with the moment I learned it.

  1. 01 / System design

    Trace the data path before changing it.

    Before writing the policy, I checked on the router how MWAN3 weights turn into iptables mangle rules and conntrack marks. Otherwise I would have been tuning numbers without knowing what they did.

  2. 02 / Problem solving

    Let the data disagree with you.

    The hypothesis was that radio-aware weights would beat static ones. The road said no measurable difference. Explaining why (bandwidth, not signal) turned out to be the most useful result of the thesis.

  3. 03 / Performance

    Measure the budget, don't assume it.

    The service shares a router with production firmware. Instead of claiming it was lightweight, I measured it: 0.5 ms of CPU per decision, 2.6 MB of memory.

  4. 04 / Testing

    Compare on the same road.

    Two policies can only be compared fairly on identical conditions, so I replayed recorded traces deterministically, and used block bootstrap because consecutive radio samples are not independent.

  5. 05 / Monitoring

    Watch it while it runs.

    During the campaigns every sample went to InfluxDB and a live Grafana dashboard, so the state of a run was visible on the road, not only afterwards.

  6. 06 / Documentation

    Every number ships with how to reproduce it.

    In SignalFlow, each benchmark result sits next to the command, parameters and hardware that produced it. A number without that is an anecdote.
